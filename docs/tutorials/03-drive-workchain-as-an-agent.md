# Drive Workchain as an agent

Workchain is designed for dual readership: human engineers via the terminal, and AI coding
agents via structured output. Every CLI command accepts `--json`. Every error has a code.
Everything an agent needs to *discover* the tool is in two files at the repo root. The MCP
server exposes the same operations over JSON-RPC.

This tutorial is written for an AI agent reading this page. A human can follow along too; the
commands are the same.

**Time:** about 5 minutes (the time to read and run each block once).
**Requires:** the CLI from [tutorial 01](01-first-chain.md), or access to the repo.

---

## Where to discover

Two files serve as the machine-readable entry points:

**`../../llms.txt`** — a plain-text index written for LLM consumption. It says what the project
is, lists its commands, describes the component model, and points at the source of truth for
the registry (`components/index.json`, generated by `lib/workchain_registry.py`). The "Start
here" block gives an agent exactly five calls to orient itself:

```text
workchain --help                      # all commands, options, exit codes
workchain components --json           # what components exist
workchain component <name> --json     # a component's params (with ranges) + outputs
workchain chains --json               # prebuilt chains and the components they use
workchain run <chain> <input> --dry-run --json   # preview the plan
```

**`../../agent.json`** — a machine-readable capability manifest (schema version 0.3). It
declares the two interfaces (CLI and MCP), every command name, every MCP tool, the exit code
table, the verification model (tiers, inbound/outbound, assert primitives, post-condition
checks), the param precedence rule, and the install requirements. An agent can read this file
without spawning the CLI.

```json
{
  "schema_version": "0.3",
  "name": "workchain",
  "interfaces": [
    {
      "type": "cli",
      "package": "@lufs-audio/workchain",
      "entry": "workchain",
      "io": {
        "structured_output": "--json on stdout",
        "progress": "newline-delimited NDJSON on stderr",
        "exit_codes": {
          "0": "success",
          "1": "execution error",
          "2": "input error",
          "3": "config error"
        }
      },
      "commands": ["run", "run-component", "components", "component", "chains",
                    "chain", "validate", "doctor", "registry", "generate", "config"]
    },
    {
      "type": "mcp",
      "implementation": "fastmcp",
      "entry": "python mcp-server/server.py",
      "transports": ["stdio", "streamable-http"],
      "tools": ["list_components", "get_step_schema", "validate_chain",
                "run_chain", "run_component", "create_component"]
    }
  ],
  "verification": {
    "prime_directive": "proven correct, not exited 0",
    "tiers": ["unverified", "verified", "certified"],
    "assert_primitives": ["exists", "non_empty", "audio_valid", "json_valid"],
    "post_condition_checks": ["json_fields_within", "audio_format_matches",
                              "content_hash_matches", "audio_lufs_within",
                              "audio_duration_matches", "stems_recombine",
                              "acoustic_roundtrip", "seed_record_verifies",
                              "embedding_wellformed"]
  }
}
```

Other discovery paths: `../../components/index.json` (the generated registry with definition
hashes and tiers), and `workchain doctor --deep` (inbound preflight across all components).

## stdout / stderr discipline

The rule is absolute:

- **stdout** — one JSON document. The entire chain result in a single parseable object.
- **stderr** — newline-delimited JSON (NDJSON) progress events, one per-line, human-readable
  and machine-parseable.

An agent MUST separate the two streams to read structured results. Use shell redirection to
handle both:

```bash
workchain run tests/normalization_only tone.wav -o ./out --json \
  > result.json \
  2> progress.ndjson
echo $?
```

`result.json` is a single object (about 130 lines on a 1-step chain). Parse it as one JSON
document:

```json
{
  "status": "completed",
  "command": "run",
  "chain": "tests/normalization_only",
  "input_file": "./tone.wav",
  "output_dir": "./out",
  "duration_ms": 1942,
  "steps": {
    "normalization": {
      "status": "completed",
      "preflight": { "satisfied": true, "checks": [{"name": "command:ffmpeg", "ok": true}], "failures": [] },
      "outputs": { "primary_output": { "path": "...", "exists": true, "type": "file" } },
      "verification": {
        "tier": "verified",
        "verified": true,
        "checks": ["... all 8 checks pass ..."],
        "failures": []
      }
    }
  },
  "warnings": []
}
```

`progress.ndjson` is three lines — one per step transition:

```json
{"progress":{"step":"normalization","status":"running"}}
{"progress":{"step":"normalization","status":"completed"}}
{"progress":{"status":"workchain_completed"}}
```

An agent can tail `stderr` for live progress, poll `stdout` for the final result, or — for
the simplest integration — just read `stdout` after the process exits.

## Exit codes

From `workchain --help`:

| Code | Meaning | When it happens | Demonstrated |
|------|---------|-----------------|-------------|
| `0` | Success | Chain completed and all verify checks passed. Or `--dry-run` generated a plan. | `workchain run tests/normalization_only tone.wav -o ./out --json` → exits 0 |
| `1` | Execution error | A step failed preflight or its `verify:` contract. The chain halted. | The off-target run from [tutorial 01](01-first-chain.md) exits 1. The JSON has `"status": "error"` and `"code": 1`. |
| `2` | Input error | File not found, unknown chain, unsupported format. | `workchain run tests/normalization_only missing.wav -o ./out --json` → exits 2. |
| `3` | Config error | `workchainRoot` misconfigured, or the engine cannot find the repo. | `workchain config set workchainRoot /tmp/no-such-root` then any command exits 3. |

Concrete example of a `2`:

```bash
workchain run tests/normalization_only /tmp/does-not-exist.wav -o ./out --json
# exit=2, JSON has: {"status":"error","code":2,"message":"Input file not found: ..."}
```

## Validate before you run

The `validate` command checks chain structure, param types, numeric ranges, and unknown params
without executing anything. Use `--strict` for full enforcement (also checks param ranges):

```bash
workchain validate tests/normalization_only --strict
# ✓ Chain 'tests/normalization_only' is valid (strict)
```

The MCP equivalent: `validate_chain(chain_file="tests/normalization_only", strict=True)`.

A validation error means the chain will fail at runtime, but the error message will be clearer
and faster. Prefer `validate --strict --json` in automated pipelines.

## The MCP door

The MCP server exposes the same operations as the CLI over JSON-RPC (stdio or HTTP). It runs
wherever Python 3.10+ is installed.

### Starting the server

```bash
pip install fastmcp    # or the equivalent uv sync/wheel
python mcp-server/server.py
```

Default transport is **stdio**. The server reads JSON-RPC requests from stdin and writes
responses to stdout. Server logs go to stderr and do not interfere with the protocol.

### The tools

Six tools, matching `agent.json`:

| Tool | Returns | Equivalent CLI |
|------|---------|----------------|
| `list_components()` | JSON string — every component (name, description, type, version, param_count) | `workchain components --json` |
| `get_step_schema(component)` | JSON string — full schema: params (type, default, range), outputs, requirements | `workchain component <name> --json` |
| `validate_chain(chain_file, strict=true)` | JSON string — valid, errors, resolved steps | `workchain validate <name> --strict --json` |
| `run_chain(chain_file, input_file, output_dir)` | JSON string — full chain result | `workchain run <name> <input> --json` |
| `run_component(component, input_file, output_dir, params_json)` | JSON string — single component result | `workchain run-component <name> <input> --params-json '{...}' --json` |
| `create_component(name, description, type, params_json, commands)` | JSON string — confirmation | `workchain generate component --name <name>` |

Every tool returns a **JSON string**, not a raw object. The agent must parse it.

### Worked JSON-RPC handshake

Standard MCP initialization:

```json
→ {"jsonrpc":"2.0","id":1,"method":"initialize",
    "params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"my-agent","version":"1.0"}}}
← {"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2024-11-05","serverInfo":{"name":"workchain","version":"3.4.7"},"capabilities":{}}}
→ {"jsonrpc":"2.0","method":"notifications/initialized"}
```

Then call tools:

```json
→ {"jsonrpc":"2.0","id":2,"method":"tools/list"}
← {"jsonrpc":"2.0","id":2,"result":{"tools":[
     {"name":"list_components","description":"List every available processing component…","inputSchema":{"type":"object","properties":{}}},
     {"name":"get_step_schema","description":"Get the full schema for one component…","inputSchema":{"type":"object","properties":{"component":{"type":"string"}}}},
     {"name":"run_chain","description":"Run a processing chain on an audio file.","inputSchema":{"type":"object","properties":{"chain_file":{"type":"string"},"input_file":{"type":"string"},"output_dir":{"type":"string"}}}},
     {"name":"validate_chain","description":"Validate a chain BEFORE running it…","inputSchema":{"type":"object","properties":{"chain_file":{"type":"string"},"strict":{"type":"boolean"}}}},
     {"name":"run_component","description":"Run a component standalone…","inputSchema":{"type":"object","properties":{"component":{"type":"string"},"input_file":{"type":"string"},"output_dir":{"type":"string"},"params_json":{"type":"string"}}}},
     {"name":"create_component","description":"Scaffold a NEW component…","inputSchema":{"type":"object","properties":{"name":{"type":"string"},"description":{"type":"string"},"type":{"default":"audio"},"params_json":{"type":"string"},"commands":{"type":"string"}}}}
   ]}}
```

### Worked tool call — list_components

```json
→ {"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"list_components","arguments":{}}}
← {"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"{\n  \"status\": \"completed\",\n  \"count\": 6,\n  \"components\": [\n    {\"name\": \"audio_benchmark\", ...},\n    {\"name\": \"cdp_transform\", ...},\n    {\"name\": \"content_hash\", ...},\n    {\"name\": \"format_conversion\", ...},\n    {\"name\": \"normalization\", ...},\n    {\"name\": \"stem_separation\", ...}\n  ]\n}"}]}}
```

Parssing: extract the `content[0].text` field and parse it as JSON. That yields the same
structure as `workchain components --json`.

### Worked tool call — get_step_schema

```json
→ {"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"get_step_schema","arguments":{"component":"normalization"}}}
← {"jsonrpc":"2.0","id":4,"result":{"content":[{"type":"text","text":"{\"status\":\"completed\",\"component\":\"normalization\",\"schema\":{\"name\":\"normalization\",\"description\":\"LUFS audio normalization using FFmpeg loudnorm filter\",\"version\":\"1.1\",\"type\":\"audio\",\"params\":[{\"name\":\"target_lufs\",\"type\":\"number\",\"default\":-11,\"range\":{\"min\":-60,\"max\":0}},{\"name\":\"two_pass\",\"type\":\"boolean\",\"default\":true},{\"name\":\"lra\",\"type\":\"number\",\"default\":7,\"range\":{\"min\":1,\"max\":20}},{\"name\":\"true_peak\",\"type\":\"number\",\"default\":-1.5,\"range\":{\"min\":-10,\"max\":0}},{\"name\":\"offset\",\"type\":\"number\",\"default\":0,\"range\":{\"min\":-6,\"max\":6}}],\"outputs\":{\"items\":[{\"name\":\"primary_output\",\"type\":\"file\"},{\"name\":\"loudness_metadata\",\"type\":\"json\"}]}}}"}]}}
```

Parse the inner text to discover the component's parameters with their types, defaults, and
ranges — before running it.

### Worked tool call — validate_chain

```json
→ {"jsonrpc":"2.0","id":5,"method":"tools/call","params":{"name":"validate_chain","arguments":{"chain_file":"tests/normalization_only","strict":true}}}
← {"jsonrpc":"2.0","id":5,"result":{"content":[{"type":"text","text":"{\"valid\":true,\"errors\":[],\"name\":\"Test: Normalization Only\",\"version\":\"1.0\",\"steps\":[{\"name\":\"normalization\",\"enabled\":true,\"params\":{...}}],\"status\":\"completed\"}"}]}}
```

## Operating rules for agents

1. **Never treat stderr as data.** It is progress and log events. The result you make decisions
   on is the JSON on stdout. Use the exit code as a first-pass gate: if exit != 0, the stdout
   JSON has `"status": "error"` and a `"code"` and `"message"` you can trust.

2. **Never trust `status: completed` without reading `verification`.** A step that exits 0
   but fails its contract is recorded `failed` — not `completed`. The `status` field at the
   chain level is `error` when any step fails verification, with exit code 1. The individual
   step's `verification.tier` tells you whether the step's output was independently proven.

3. **Process the `verification` block before using the output.** The output file exists on
   disk at the path in `outputs.primary_output.path`. The verification block tells you whether
   that file is actually what was required. Use it; do not open the file first.

4. **Parse the inner JSON.** Every MCP tool returns a JSON string embedded in the standard MCP
   content wrapper. The agent must `JSON.parse(content[0].text)` to get the actual result.

5. **Validate before you run.** `validate_chain(chain_file, strict=True)` is cheap, catches
   param type errors and numeric range violations, and fails with clear messages. Running an
   invalid chain wastes time and may leave partial output.

6. **Disover before calling.** `list_components()` and `get_step_schema(component)` give you
   the full param schemas with types and ranges. Do not guess param names — they are
   discoverable. Rely on the schema, not on what a README says (though READMEs are kept honest
   in this repo).

## What a failure looks like in data

An agent that reads only `exit_code == 0` will miss the most important class of failure. The
off-target run from [tutorial 01](01-first-chain.md) produces:

```
exit_code: 1
stdout JSON status: "error"
stdout JSON code: 1
stdout JSON message: "Chain halted: step 'normalization' failed verification"
details.steps.normalization.verification.tier: "unverified"
details.steps.normalization.verification.failures:
  [{ name: "integrated_loudness_on_target", detail: "measured -8.95 LUFS vs target -5.0 (±1.0) → off by 3.95 LU" }]
stderr NDJSON:
  {"progress":{"step":"normalization","status":"failed","error":"verification","checks":["integrated_loudness_on_target: measured -8.95 LUFS vs target -5.0 (±1.0) → off by 3.95 LU"]}}
  {"progress":{"status":"chain_halted","step":"normalization"}}
```

An agent tasked with reporting whether the step succeeded MUST:
1. Check exit code (non-zero → problem).
2. Read `status` from stdout JSON (`"error"` → problem).
3. Look at `details.steps.<name>.verification.verified` / `tier` / `failures` — this tells you
   what was proven and what failed. Never use the component's own output metadata.
